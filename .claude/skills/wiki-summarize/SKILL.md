# wiki-summarize — 知识库总结梳理

> 对一个已经存在的知识库做一次全面"体检 + 梳理"，产出一份可直接阅读、可交付的总结报告。
> 本 skill 已适配 llm_wiki 仓库的**多知识库**结构。

## 适用范围

- **llm-wiki 风格知识库**：根目录含 `.wiki-schema.md`，有 `raw/`（原始素材）+ `wiki/`（entities/topics/sources/...）+ `index.md` / `overview.md` / `log.md` 结构
- **任意 Markdown 知识目录**：降级模式，同样可用（见文末）
- **本仓库特例**：`E:\llm_wiki` 下同时存在 `ai-wiki/` 与 `stock-wiki/` 两个独立知识库，**每个库单独产出一份 SUMMARY.md**，不要混在一起写

## 执行流程（五步，不可跳步）

### 第 1 步：定位知识库根

按顺序尝试，命中即止：

1. 用户明确给出了路径或库名（`ai-wiki` / `stock-wiki` / 具体目录）→ 直接用
2. 当前目录含 `.wiki-schema.md` → 当前目录
3. 当前目录下存在**多个**子目录含 `.wiki-schema.md` → 列出这些库，**问用户要梳理哪个**（可多选，逐个产出报告）
4. 存在 `~/.llm-wiki-path` 文件 → 读其内容作为路径，并确认目录存在
5. 以上都没有 → **问用户**，不要猜

> 本仓库在 `E:\llm_wiki` 根目录执行时命中第 3 条。

### 第 2 步：结构扫描（只读，不改任何文件）

```bash
bash "<本skill目录>/scripts/scan-wiki.sh" "<知识库根目录>"
```

脚本输出六段：目录统计 / 页面清单 / 断链 / 孤页 / 疑似未消化素材 / 过短与占位页面。
这是报告"客观事实"部分的唯一来源；主观归纳（第 3、4 步）建立在它之上。

依赖：bash 4+ 与 GNU coreutils。Windows 下用 Git Bash 执行（本机已验证 bash 5.2 / MSYS 可用）；
**不要**用 cmd 或 PowerShell 直接跑 `.sh`。

### 第 2.5 步：交叉校验（可选）

若库里存在 `llm-wiki-skill/scripts/lint-wiki.sh`，可追加运行作交叉校验：

```bash
bash .claude/skills/llm-wiki-skill/scripts/lint-wiki.sh <库名> links sources content
```

两者结论冲突时，**以 scan-wiki.sh 为准**（它同时覆盖孤页与未消化素材），在报告里注明差异。

### 第 3 步：通读核心页面（按此优先级）

1. `.wiki-schema.md`、`index.md`、`overview.md`、`log.md`（配置、全局视角与历史）
2. **全部主题页** `wiki/topics/*.md`（逐页读正文）
3. **全部实体页** `wiki/entities/*.md`（读正文，不能只看标题）
4. `wiki/sources/`、`wiki/comparisons/`、`wiki/synthesis/` 浏览，重点页细读
5. `raw/` 只看文件名与开头几行（判断主题归属），**不全文读**——raw 是素材，报告只到"消化状态"层面

### 第 4 步：撰写梳理报告

写入 `<知识库根>/SUMMARY.md`。若已存在旧报告，先把旧文件改名为 `SUMMARY-<旧文件修改日期>.md`，再写新的。

报告固定结构（六节）：

```markdown
# 知识库梳理报告（YYYY-MM-DD）

## 1. 总览
一句话定位这个知识库 + 数字盘点表（素材数 / 实体页 / 主题页 / 其他页 / 发现问题数）

## 2. 主题地图
Mermaid 图（graph TD 或 mindmap）：主题 → 其下实体，最多两层，节点 ≤ 20 个

## 3. 分主题要点
每个主题一小节。要点必须来自实体页实际内容，每条要点末尾标注来源页 [[链接]]。
主题数量多时优先覆盖内容最厚的 5-8 个主题。

## 4. 素材覆盖
raw/ 各分类：已消化（对应 wiki 页存在）/ 疑似未消化 清单

## 5. 健康检查
脚本发现的问题逐条列出（断链 / 孤页 / 过短页 / 占位文本），每条附影响说明。
零问题时明确写"未发现问题"。

## 6. 待补全建议
明显缺失的主题、实体、关系（gaps），按优先级 ≤ 5 条，每条一句话说明理由。
```

**内容铁律：**

- 所有 `[[链接]]` 必须与实际文件名（去 `.md`）精确一致（含空格），**禁止悬空链接**
- 要点必须来自页面实际内容，禁止编造；引用原文必须逐字并注明出处页
- 引用 wiki 页用 `[[链接]]`，引用 raw 素材文件用相对路径（如 `raw/tweets/xxx.md`）
- 报告语言跟随知识库正文语言（本机默认中文）

### 第 5 步：收尾

向用户报告：报告绝对路径、主题/页面/问题数的两三行摘要。

**不要擅自 commit / push。** 用户明确要求提交时，遵循仓库 `AGENTS.md` 的约定：

```bash
git add -A
git -c user.name=wanglei9927 -c user.email=leiwang9927@gmail.com commit -m "梳理知识库：<库名>"
git push mywiki main
```

## 降级模式（非 llm-wiki 目录）

根目录无 `.wiki-schema.md` 时：

- 跳过"素材覆盖"节，主题按子目录 / 文件名聚类
- 其余步骤与报告结构不变
- 在报告"总览"注明"非 llm-wiki 结构，已用降级模式"

## 常见错误

- 把 SUMMARY.md 自己算进页面统计 / 链接索引 → 脚本已排除，Agent 撰写时也勿引用它
- 只读 index/overview 就写报告 → 要点会与实体页脱节，必须逐页读 wiki/
- 报告里发明新 `[[链接]]` 想当然"应该有这个页面" → 链接只能指向已存在的文件；缺的页面写进"待补全建议"
- 把 `ai-wiki` 和 `stock-wiki` 混在一份报告里 → 每个库独立成文
