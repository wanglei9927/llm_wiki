# Claude Code 实战开发术：让 Claude 自证，人只看不可逆

> にく（@29meat_ai）2026-10-30 长文。核心不是"少验证"，而是把可自动验证的部分交给 Claude，人只负责不可逆决策与最终责任。

## 核心观点

1. **团队自报数据**：Claude Code 自身约 90% 的代码由 Claude 编写；2026 年 6–9 月，合入变更量翻倍以上，事后需要回滚的变更比例下降 40% 以上；引入 Claude 评审后，带有"有意义指摘"的变更比例从 16% 升到 54%。作者明确提醒：这是团队自己的运营报告，不是可复现实验，也没有把判断与责任一并外包。

2. **不是不验证，而是换人验证**：可运行、可自动检查的部分先交给 Claude 与工具；人只看"必须由人决定"的部分。团队还把"漏掉问题后返工的时间"算进人的负担，避免验证时间只是转移到善后。

3. **实战术①：要证据，不要"完成了"**。让 Claude 给出实际执行的命令与结果、启动截图、试过的操作与结果、以及"未能验证的部分及原因"。开始前先让 Claude 提出最多 5 种可亲手验证的完成标准。

4. **实战术②：评审交给"不知情的另一个 Claude"**。用 `/code-review` 或新开会话；不要把"已经修好了"先告诉评审者。团队还会让多个 Claude 分头找问题、再由另一批 Claude 核实指摘，只保留确认成立的，去掉风格偏好，并区分"本次变更引入的问题"与"原本就存在的问题"。`CLAUDE.md` 保持短小，只写前提、禁区与完成报告方式。

5. **实战术③：给修复循环设上限**。团队曾出现一晚 50 多次评审往返；事后发现被反复指摘的部分约 59% 是最初就存在的代码。对策：评审 3 次后人重新判断；从第 2 次起只看新增变更；不重复提同一指摘；同类问题合并；旧问题另找时间统一处理。同一个 bug 修 2 次仍不好就停，要求汇报"试过什么 / 变了什么 / 还剩下什么 / 需要人决定什么"，并且不要碰无关区域。

6. **实战术④：安全不能只停留在警告**。团队有独立的安全自动评审，发现问题必须"修掉"或"写明理由判定为误报"才能继续。作者还列了三类风险：PHP 的 PHP2Shell（严重度 9.2，10 月 21 日修复）、Linux CVE-2026-98432（10 月 27 日 Anthropic 披露，Debian / Oracle Linux 已修复，Ubuntu / Red Hat 当时未修复）、下载文件夹中的恶意 `AGENTS.md` / `CLAUDE.md` 被 agent 当作指令执行（实验称 Codex 超过 9 成中招，Claude Code 约一半）。

7. **实战术⑤：人只看不可逆的地方**。涉及金钱与支付、登录与权限、个人隐私、公开发布、数据删除的变更，必须人自己确认；规则是"Claude 的 OK 不等于人的 OK"，而且人确认后 Claude 又改了任何地方，就要重新确认。此外，"到底要不要做这个功能"也只能由人决定。

8. **实战术⑥：随时能回滚**。小步提交、小步委托、大改前先提交当前状态、先自己用几天再给 1–2 个人用，最后才公开。原文引用团队说法 "You land it, you own it"：合入的人对结果负责，而敢负责的前提是能快速退回。

## 实操内容保留

### ① 要求证据的报告模板（原文）

```text
作業が終わったら、「完了しました」とだけ言わずに、次を見せてください。

・実際に実行したコマンドと、その結果
・アプリを起動して、画面のスクリーンショット
・試した操作（例：予約を登録して、一覧に出るか）とその結果
・確かめられなかったことがあれば、その理由
```

### ② 开始前让 Claude 提出验收方式（原文）

```text
これから〇〇を作りたいです。まだ作り始めないでください。

完成したと言えるかどうかを、私が自分で触って確かめられる方法を、5つ以内で提案してください。
それぞれ、どんな操作をして、どうなっていれば合格かを書いてください。
```

### ③ 独立评审的委托模板（原文）

```text
この変更を確認してください。まだコードは変更しないでください。

・指摘ごとに、根拠になるファイルと行を示してください
・書き方の好みに関する指摘は不要です
・今回の変更で生まれた問題と、前からあった問題は分けてください
・問題がなければ「問題なし」とはっきり書いてください
```

### ④ 停止修复循环的模板（原文）

```text
同じ不具合を2回直しても解決しなかったら、それ以上の修正は止めてください。

止めたら、次の4つをまとめて教えてください。
・試したこと
・変わったこと
・まだ残っている症状
・私が決める必要があること

今回頼んだ不具合と関係ない場所は、直さないでください。
```

### ⑤ 安全评审模板（原文）

```text
このアプリを公開する前に、セキュリティの確認をしてください。
まだコードは変更しないでください。

・ログインしていない人が、他の人のデータを見られないか
・パスワードやAPIキーが、コードやファイルに直接書かれていないか
・使っている部品やサーバーに、更新が必要なものがないか

見つかった問題ごとに、根拠になるファイルと行、影響、直し方の案を出してください。
確かめられなかったことは、「未確認」と書いてください。
```

### ⑥ 大改前的回滚点模板（原文）

```text
作業を始める前に、今の状態をGitにコミットしてください。
メッセージは「〇〇の変更前」としてください。

作業が終わって、動くことを確認できたら、もう一度コミットしてください。
うまくいかなかった場合は、変更前のコミットに戻す方法を教えてください。
```

### ⑦ 只解释要触碰的部分（原文）

```text
予約を消す機能の仕組みを、コードが読めない人向けに説明してください。

・ボタンを押してから、データが消えるまでの流れ
・データがどこに保存されているか
・失敗しやすいところ

できれば、流れを図にしてください。
```

## 端到端流程（预约应用示例）

1. 新建工作文件夹，不在下载文件夹启动 Claude Code
2. 写短版 `CLAUDE.md`：做什么、不做什么、完成报告方式
3. 先提交当前状态，建立可回退起点
4. 小步委托：先只做"预约登记 + 列表"
5. 要求带证据的完成报告：登记 → 出现在列表 → 刷新后仍在
6. 交给另一个 Claude 评审：`/code-review` 或新会话
7. 修复往返最多 2 次，超过就停下汇总，由人判断
8. 确认能跑就提交，再进入下一个功能
9. 发布前跑 `/security-review`
10. 只亲手测试不可逆部分：删除预约、发布设置等

## 常见 NG

- 只问"做好了吗" → 几乎一定得到"做好了"
- 说"弄得好看点" → 没有可验证的完成标准
- 权限请求全部无脑同意 → 删除、外发、发布相关必须读清楚
- 直接让 agent 读下载来的文件 → 可能藏有注入指令
- 能跑了不提交 → 下次改坏没有回退点
- 一次性把所有 bug 丢过去 → 无法判断哪个修好了，原因也追不到

## 关键概念

- **证据式完成报告**：完成 = 实际执行结果 + 截图 + 试过的操作 + 未验证项，而不是一句"完成了"。
- **独立评审者**：不带原会话上下文的另一个 Claude，避免被"已经修好"的预设带偏。
- **修复循环上限**：评审次数与同一 bug 的修复次数都要设上限，超过就交回人判断。
- **不可逆区域**：支付、认证、隐私、发布、删除，只能由人最终确认。
- **可回滚优先**：小步提交、大改前留回退点、分阶段发布。
